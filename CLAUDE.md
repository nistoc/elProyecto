# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Pipeline for transcribing Spanish lesson audio recordings: audio → diarized transcript (OpenAI `gpt-4o-transcribe-diarize`) → "refining" (fixing Spanish words the ASR wrote in Cyrillic, e.g. «пор фавор» → «por favor») → web UI to monitor jobs and edit transcripts. Three services, one monorepo:

| Directory | Service | Stack | Port |
|---|---|---|---|
| `agent04/` | Transcriber | .NET 9, **gRPC only** (no REST) | 5032 (h2c) |
| `agent06-improver-dot-net/` | Refiner (TranslationImprover) | .NET 9, gRPC (h2c) + REST | 5033 gRPC / 5034 REST |
| `agent05-ui-control/` | Orchestrator API (XtractManager) + React UI | .NET 9 + React 18/Vite/TS | 5010 / 5173 |

A first generation in Python (`agent01`, `agent03-trans-improver`, Node `agent-browser`) was removed in commit `88b7477`; retrieve from git history if ever needed. agent04/agent06 keep artifact and config formats compatible with it, which is why code comments still reference agent01/agent-browser.

## Commands

Each .NET service builds from its project dir (solutions are `.slnx` files at each agent root):

```bash
# agent04 (run from agent04/Agent04), agent05 API (from agent05-ui-control/API),
# agent06 (from agent06-improver-dot-net/API):
dotnet build
dotnet run

# tests — run from the agent root or the *.Tests project dir:
dotnet test
dotnet test --filter "FullyQualifiedName~OperatorChunkSplitPlannerTests"   # single class/test

# UI (from agent05-ui-control/UI):
npm install
npm run dev            # Vite on 5173, proxies /api and /health to :5010
npm run build          # tsc -b && vite build
npm run test           # vitest run
npm run test -- chunkArtifactGroups   # single spec
npm run lint           # eslint
npm run format         # prettier --write
```

Startup order for the full pipeline: agent04 and agent06 first, then agent05 API, then UI. Requirements: .NET 9, Node 18+, `ffmpeg`/`ffprobe` on PATH, `OPENAI_API_KEY` (agent06 reads it from a gitignored `.env` in `agent06-improver-dot-net/API/`).

## Cross-service contracts (the important invariants)

**Workspace root.** All three services operate on one shared jobs directory, currently `D:/trash/spanish/elProyecto/runtime` (outside the repository, on an external disk: moved there on 2026-11-18 to free drive C, the code stayed on drive C). Layout: `{workspace}/{jobId}/` holds the uploaded audio and every artifact. Config keys that must stay in sync: `WorkspaceRoot` in `agent04/Agent04/appsettings.json`, `WorkspaceRoot` in the gitignored `agent06-improver-dot-net/API/.env`, `Jobs:WorkspacePath` + `Agent04:WorkspacePath` in `agent05-ui-control/API/appsettings*.json` (`Agent06:WorkspaceRoot` empty = falls back to `Jobs:WorkspacePath`). agent04 and agent06 **exit at startup** if their `WorkspaceRoot` doesn't exist — with the disk not connected nothing starts. All paths in gRPC requests are relative to the receiving service's workspace root; agent05 passes `job_directory_relative` (= jobId) so agent04/agent06 write into the job folder.

**Job flow.** UI `POST /api/jobs` (multipart) → agent05 stores file, runs pipeline in background (`TranscriptionRefinerPipeline`): gRPC `SubmitJob` to agent04 → consumes `StreamJobStatus` server-stream → on Completed reads `transcript.md`, submits to agent06 `SubmitRefineJob` → streams refine status → done. UI receives updates via SSE `GET /api/jobs/{id}/stream` (events: `snapshot` | `status` | `done`; first event is always a full snapshot). Job phases: `idle → transcriber → awaiting_refiner → refiner → completed`.

**Refine run.** The refiner never starts by itself: UI «Run Refiner» → agent05 `POST /api/jobs/{id}/refine`, body `{skip, inputFile, prompt}`. `prompt` (`RefinerRunPlan`): `lesson` — the run about the words in doubt, `candidates_only` (field 19 in both copies of `refine.proto`): agent06 finds by code the words that may be Spanish written in Cyrillic or that mix letters of both alphabets (`SpellingCandidates`: the exact sound of a word the transcript has in Latin letters), asks the model only in which language each was said (`OpenAISpellingJudge`, ten words to a request, every request put to two models — the model of the request, default `gpt-4.1-mini`, and `gpt-4.1` — and a word written anew only when both name the same language, or when `gpt-4.1` alone says Spanish and the transcript has the word in Latin letters in the same line or the one next to it — `CandidateRespelling.NamedNextTo`), and writes the spelling itself (`CandidateRespelling`); no line comes from the model, a request shows in the UI with the words it asked about (`asked_words`), and the run record `*.prompt.md` lists the words written anew and why the others stayed; `saved` or nothing — the settings of the Refiner tab, every line sent and taken as the model wrote it. agent06 still has the check of a run that sends every line, `respelling_only` (field 18, `RespellingGuard`: of the model's changes only a word in Cyrillic respelled in Latin letters that sounds alike, occurs in the transcript in Latin letters and has Spanish next to it is kept); agent05 no longer asks for it. The snapshot's `lesson` (the job folder has `track_source.json` or `dialogue.json`) makes the UI offer `lesson` first. The saved settings may hold a prompt for another material — a lesson refined with them is harmed. A job agent05 finds on disk (every job after its restart) is taken into the in-memory store on its first update (`IAdoptingJobStore`; phase and status from `xtract_ui_state.json`, chunks still read from the folder), so its phase follows the run and a second start gets 409; a phase `refiner` left in that file for a job the process does not hold reads as `awaiting_refiner`/`failed` (the run died with the old process).

**Job artifact layout** (inside `{workspace}/{jobId}/`): source audio, `transcript.md`, `transcript_fixed*.md` (refiner output), `response.json`, `chunks/`, `chunks_json/`, `converted_wav/`, `intermediate_results/`, `split_chunks/chunk_N/` (operator splits; `sub_chunks_timeline.json` there keeps where each part starts inside the chunk, the merge of the parts reads it), `transcription_work_state.json` (chunk progress on disk), `timeline/chunks.json` (each chunk's offset and overlap guard in the audio that was split; rebuild and retranscribe read it), `timeline/speech_map.json` (only when silence was cut out: kept pieces of the source and their place in the compressed file; md writers use it to print times of the recording), `track_source.json` (only when the job was started from the lessons list: which file of the recordings folder it transcribes), `job_settings.json` (only when the operator chose settings for this job at upload: pause kept, compression, model; agent04 puts them on top of the shared config), `run_settings.json` (what the job started with: model, compression, pause kept, which keys came from `job_settings.json`; agent04 writes it in `SubmitJob`, agent05 shows it as `runSettings` of the job and reads the run's artifacts instead for jobs older than the record), `pending_chunks.json` (indices for next run, written by `EnqueueTranscriptionWork` gRPC).

**Dialogue jobs.** agent05 `POST /api/jobs/dialogue` merges the combined transcripts of participant-track jobs (one job per Zoom participant file) into a job folder of its own: `transcript_dialogue_<stamp>.md` (speaker labels replaced by participant names, lines in time order) plus `dialogue.json` (tracks and merge log). No audio, no agent04 call; the source jobs are only read, and the job waits in `awaiting_refiner` like any other. `POST /api/jobs/{id}/dialogue/rebuild` writes a new merge next to the old ones.

**Language share.** agent05 `GET /api/jobs/{id}/language-share` (`JobLanguageShareReader`, read on request, not part of the snapshot) counts the seconds of Spanish, Russian and mixed lines from the segments of `chunks_json/*.json` — the script tells the language (a line is Spanish from 70 % Latin words, Russian up to 30 %); a dialogue job gets one entry per track of `dialogue.json` and their sum. UI: lines under the run settings of the job view. Spanish written in Cyrillic (the diarize model) counts as Russian. A segment inside the chunk's `emit_guard_sec` is not counted. A dialogue whose tracks can all be put on the timeline of the recording (`JobTimedLinesReader`: `timeline/chunks.json`, plus `timeline/speech_map.json` when silence was cut; no chunk merged from operator parts) also gets `conversation` (`ConversationStats`): seconds of joint speech and of silence, and per participant the interruptions (a line begun over another's speech that then goes on together with it for 1 s), short assents, the usual wait before an answer and the pauses from 3 s before an answer and in their own speech; `null` otherwise. A pause under a second inside a line counts as speech, so the joint seconds are an upper estimate. Each run of a track in `GET /api/sessions` carries the same `share`; `JobLanguageShareCache` keeps it in memory and counts it anew when the number, size or newest write time of the answer files changes (the first list after a start counts all jobs in parallel). UI: «es 74 % · ru 18 %» next to the run in the lessons list.

**Lessons from the recordings folder.** agent05 `Recordings:RootPath` (currently `D:/trash/spanish`, the same external disk) is **read only**: `GET /api/sessions` scans it into lesson (day folder `YYYY.MM.DD[ title]`, or Zoom period folders left in the root) → period (`YYYY-MM-DD HH.mm.ss <meeting>` folder, or a flat audio file of an old day) → track (`mixed` = `audio<id>.m4a`, `participant` = `Audio Record/audio<Name><N><id>.m4a`) and ties jobs of the workspace to tracks (`TrackRunsIndex`: by `track_source.json`, by name + size of the audio in the job folder, by size + first 64 KB). `POST /api/sessions/runs` copies a track into a new job folder, writes `track_source.json` and queues the usual (paid) pipeline; a participant track whose settings name no model gets `Recordings:ParticipantTrackModel` (default `gpt-transcribe`) written into its `job_settings.json`, the mixed track and a plain upload stay on the shared model. UI: the "Lessons" panel (`LessonsPanel.tsx`).

**Lessons by groups of days.** agent05 `POST /api/sessions/batch` (`LessonBatchController`, the plan is made by the pure `LessonBatchPlanner`) takes a list of lesson dates and answers what each lesson still misses to have its text: a `run` for a track no job transcribed (participant tracks when a recording has them, else its mixed file — on `Recordings:MixedOnlyTrackModel`, default `gpt-transcribe`), `wait` for a job queued or going, `failed` for a track whose runs ended without a transcript (run again only with `retryFailed`), `duplicate` for a file that lies in the day twice (size + first 64 KB), `dialogue` once every participant track of a recording has text. Without `dryRun: false` nothing is started (the answer is the plan with minutes and an estimate); with it the runs are queued (paid) and the dialogues merged, unless the estimate is above `maxUsd` (409). It keeps no state: every call reads the folders anew, so a second call does only what is missing. A refine is never started by it. Runs of one call do not all go at once: `PipelineBackgroundService` lets `Pipeline:MaxParallelJobs` transcriptions (default 4) go and holds the rest as `queued`; a refiner run does not wait. `GET /api/sessions` gives every lesson a `stage` (`LessonStage`: `no_recording`, `no_text`, `partial`, `transcribing`, `dialogue_pending`, `text_ready`, `package`). `TrackRunStarter` is the one way a track becomes a job — for `POST /api/sessions/runs` and for the batch.

**Lesson text with speakers.** agent05 `GET /api/sessions/{date}/text` (`LessonTextController`, `LessonTextReader`) gives every recording of a lesson in one answer, each line with its time, speaker and role — what a package is built from. The text of a recording is chosen as `LessonWordIndex` chooses it (newest dialogue, else newest run of each track, participant tracks before the mixed file, else the other service's answer in the day folder); only raw transcripts are read. A mixed recording transcribed without speakers (`gpt-transcribe`) gets the speakers of the other service's answer that lies next to its audio (`OtherServiceAnswer.For`: the answer whose name starts with the audio's name): `SpeakerOverlay` finds our words among the heard words by sound (`SaidText.SoundForm` — the other service writes Spanish in Cyrillic), gives every word the speaker of the heard word it stands at, and cuts the line where the speaker changes (`overlayWordsMatched` of `overlayWords` tells how much was found: 58–74 % on the August 2025 recordings). Roles: a role given by a person (`PUT /api/sessions/{date}/text/speakers`, kept in `{packages}/{date}/speakers.json` by `FileLessonSpeakersStore`) or by a track label «Преподаватель»/«Ученик» stands; otherwise `LessonRoleGuess` guesses — of the two who say most, the one with more words is the teacher (33 of 33 on role-labelled recordings, 2026-11-20; a larger share of Spanish was right in only 29); a small stray label of the other service gets no role.

**Lesson pages.** The page of a lesson (the lesson package: vocabulary, topics, grammar, new words) is made outside the services; agent05 keeps only its address so the lesson can show a link. `PUT` / `DELETE /api/sessions/{date}/pages` (`ILessonPagesStore`, `FileLessonPagesStore`) write `lesson_pages.json` in the workspace root — by lesson date, an absolute http(s) address and an optional title; the recordings folder stays read only, and a file in the workspace root is not a job (jobs are folders). `GET /api/sessions` gives every lesson its `pages`. The file may be edited by hand: each address is checked again on read, and a file that cannot be read is never written over (409); fields added to it by hand are kept by the next write, and a change that cannot be written (no jobs folder — it is not made for this file) gets 500 with the reason. UI (`LessonPageLinks`): the link stands next to the lesson date in the jobs list, in the line "Lesson · recording" above an open job of that lesson, and at the lesson in the "Lessons" panel, where a form puts and removes it. The lessons list is read by the app once (`useLessonJobs` in `App.tsx`) and again when a job appears, changes phase, or a page link is changed.

**Lesson packages.** The package of a lesson (topics, grammar spoken of, examples, new words, vocabulary, words found by code) is shown by XtractManager itself. **Before changing anything of it read `lesson-package/CLAUDE.md`** — the owner's requirements, the rules that must hold, the data contract (`CONTRACT.md`), how the lists are built (`BUILDER.md`) and the prompt of every pass (`prompts/`). In short: the lists lie in `{packages}/{YYYY-MM-DD}/package.json`, written by the builder only (`lesson-package/builder/`, Python, standard library: `python -m builder build <date>…` from `lesson-package/` reads a lesson from agent05 `GET /api/sessions/{date}/text` and `GET /api/sessions/words?before=`, asks the passes of `BUILDER.md` — OpenAI, paid, under `--max-usd`, or request files another hand answers — and `publish` copies the package into `{packages}`; `python -m builder days <date>…` takes a group of days from the recordings to the packages: it asks `POST /api/sessions/batch` with `dryRun: true`, starts the missing transcriptions only with `--transcribe-max-usd`, builds the lessons whose text is whole and stops with its own exit code at every step that waits for a person or for a run) and never rewritten by the service; `{packages}` is `LessonPackages:RootPath`, by default the folder `lesson-packages` next to the jobs folder — not inside it, where every folder is a job. agent05 `GET /api/sessions/{date}/package` (`LessonPackagesController`, `LessonPackageViewBuilder`) gives every item an id made of the builder's own text, puts the owner's edits on and counts for every word the earlier lessons that have it (`LessonWordRules`; the words of the lessons are read from the transcripts in the job folders by `LessonWordIndex` — per recording the newest dialogue, else the newest run of each track; of a job its raw transcript, and of its refined one only the Latin-letter words the raw text has in the same letters or with the same sound (`SaidText`: an old refine wrote Russian lines in Spanish, and those words were not said), the chunk answers standing in for a raw transcript that was not kept; a lesson no job transcribed is read from the answer files of another recognition service in its day folder (top-level `*.json`) — and cached in memory by the size and write time of the files, so the first read after a start is slow). `PUT` / `DELETE /api/sessions/{date}/package/marks/{id}` keep an edit — fields written anew, an item taken out — in `marks.json` next to the package (`FileLessonPackageStore`; a file that cannot be read is never written over, unknown entries and fields are kept). `GET /api/sessions/tracks/audio?track=` streams a file of the recordings folder with HTTP range, for playing a phrase from its place. `GET /api/sessions` gives every lesson `package` (`{builtAt}` or null). UI: the button «Пакет урока» of `LessonPageLinks` opens `LessonPackageView` in place of the job view — tabs words / grammar / topics / examples, the words table (`LessonPackageWords`: only the words no earlier lesson has by default, lists, search, sorting, columns dragged and kept in `localStorage`), every text edited in place (`EditableText`), a player at the bottom.

**Job config contract.** agent04 job configs (`agent04/Agent04/config/default.json`) use the legacy agent01 JSON schema: `file`, `model`, `openai_api_key: "env:OPENAI_API_KEY"`, `pre_split`, `target_chunk_mb`, `parallel_transcription_workers`, `md_output_path`, etc. One job can override `silence_compress_enabled`, `silence_keep_sec` and `model` without touching that file: UI upload form → agent05 `POST /api/jobs` form field `settings` → `{jobDir}/job_settings.json` → agent04 `JobSettingsFile.Apply` in `SubmitJob` and the chunk commands.

**gRPC over plain HTTP (h2c).** No TLS anywhere locally. agent05's client sets `Http2UnencryptedSupport`; agent04's Kestrel listens on 5032 as HTTP/2-only (`ConfigureKestrel` in `Program.cs`). agent06 does the same on 5033 (gRPC) and serves REST/health on 5034. Breaking this yields `HTTP_1_1_REQUIRED` errors.

## agent04 internals (where most work happens)

Vertical slice in `agent04/Agent04/Features/Transcription/` split Domain / Application (interfaces + models) / Infrastructure (implementations); DI wiring in `Composition/Agent04ServiceRegistration.cs`; gRPC surface in `Services/TranscriptionGrpcService.cs` + `Proto/transcription.proto`. Key concepts:

- **Chunking**: audio is pre-split by ffmpeg into `chunks/`, transcribed with a sliding-window scheduler (`parallel_transcription_workers`, clamp 1–64), cached by SHA256 fingerprint, merged in index order into Markdown/JSON. A chunk the server refuses three times (HTTP 5xx) is cut into `server_error_split_parts` parts (config, default 4) and put back as one timed answer of the chunk (`ServerErrorChunkSplit`; block `auto_split` in the chunk's JSON) instead of becoming one line without time marks. A refusal that concerns the account (`TranscriptionWorkflowAbort.RefusalReason`: `insufficient_quota`, `invalid_api_key`, 401…) is thrown as `TranscriptionAccountRefusedException` after one request, is never retried or swallowed (also not by `SpeechPiecesTranscription`, which would otherwise store a chunk of unanswered pieces as completed), and stops the whole job with that reason as the job's error.
- **Plain-text model (`gpt-transcribe`)**: a job whose `model` starts with `gpt-transcribe` (job settings; the shared default stays the diarize model) goes through `SpeechPiecesTranscription` — the chunk is asked whole and in pieces cut at its pauses (`SpeechPiecePlanner`, silence found inside the chunk file), the whole text is laid onto the pieces by word alignment (`SpeechPieceWordAlignment`), and the answer is assembled in the shape of a timed one (block `speech_pieces` in the chunk's JSON), so cache, md writers, retranscribe and sub-chunks need nothing special. It writes Spanish in Latin and Russian in Cyrillic (`speech_pieces_languages`, `speech_pieces_prompt` in the shared config) and has no speakers — meant for participant tracks. The whole-chunk request names the languages in its own order (`speech_pieces_whole_languages`, `ru` first): with `es` first the model wrote Russian phrases of a long stretch in Spanish (translated them); to see that error, set a line against `own_text` of its piece — two runs agreeing proves nothing. A runaway answer (more words than the audio can hold, or one word 20 times in a row) is dropped and asked again. A piece that got no word of the whole text keeps what it heard alone; where that is Cyrillic, `SpeechPieceSecondLook` respells it by the neighbour line it repeats, else by the piece asked again with `speech_pieces_context_sec` of audio around it (the run of Latin words that sounds like the piece). A line that is Spanish where its piece alone is Russian and does not sound like it (`LooksTranslated`) is asked the same way and replaced only when that answer has what the piece heard alone, with a Russian word in it, and nothing closer to the line (`SaidAsHeardAround`; a line that is word for word a part of the piece's own text is not doubted; block fields `lines_asked_with_context`, `lines_taken_from_context`, item `whole_text_line`). The mirror — a Russian line over a piece that alone is Spanish (`LooksWrittenInRussian`) — is asked the same way and replaced on a higher bar (`SaidInSpanishAround`: a run with a Spanish word at least 0.8 like the piece, and no Russian word of the line heard in that answer), because there the piece alone is the one that errs more often.
- **Operator chunk commands** (`ChunkCommand` gRPC, driven from the UI's chunk panel via agent05 `POST /api/jobs/{id}/chunk-actions`): cancel (cooperative, via per-job cancel-flag dir `.agent04_chunk_cancel/` + HTTP CancellationToken), split into sub-chunks (`split_chunks/chunk_N/sub_chunks/`), transcribe_sub, retranscribe, rebuild_combined/rebuild_split_merged, DeleteSubChunk. Retranscribe writes the chunk's `chunks_md/*.md` anew only when it still is what the previous answer rendered to — an md the operator edited is never overwritten (rebuild_combined never overwrites an existing chunk md either).
- **"RENTGEN" / virtual model**: a node tree (`INodeModel`, `ChunkVirtualModelFromWorkState`, VM merge) describing per-chunk state for the UI; docs in `agent04/docs/RENTGEN_IMPLEMENTATION.md` and `CHUNKS_AND_RENTGEN.md`.
- `Agent04.Tests/ChunkArtifactGroupingTests` optionally scans a real sample job under the repo-root `runtime/` — it no-ops if the folder is absent.

## Conventions

- Conventional commits with agent scope: `feat(agent04): …`, `chore: …`.
- Console log timestamps are **UTC** in all services (configured in each `Program.cs`) — keep it that way.
- API/frontend standards and parity docs live in `agent05-ui-control/docs/` (`API_STANDARDS.md`, `FRONTEND_STANDARDS.md`, `JOB_FILES_SCANNER_AND_AGENTS.md`); agent04 behavior docs in `agent04/docs/`.
- READMEs are the source of truth for endpoint tables: root `README.md` (topology), plus each agent's `README.md`.
